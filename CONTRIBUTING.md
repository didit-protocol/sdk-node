# Contributing

Thanks for helping with the official Didit TypeScript / JavaScript SDK.
Read [docs/DESIGN.md](docs/DESIGN.md) first: it is the contract shared by all seven Didit server SDKs, and when this code and the design disagree, the code is wrong.

## Setup

You need Node.js 22.18 or later (the generator runs TypeScript directly) and pnpm (`corepack enable`).
The SDK itself supports Node.js 18 or later; CI tests every supported version.

```sh
pnpm install
```

## Commands

| Command               | What it does                                                                            |
| --------------------- | --------------------------------------------------------------------------------------- |
| `pnpm generate`       | Regenerate `src/resources`, `src/types`, `tests/generated` and `api.md` from `openapi/` |
| `pnpm generate:check` | Fail when the generated code differs from what `openapi/` produces (CI)                 |
| `pnpm test`           | Unit, generated, contract, webhook and Authentication tests (no network)                |
| `pnpm test:coverage`  | The same with the core coverage gate (90 % of lines, statements, functions, branches)   |
| `pnpm test:live`      | Live smoke tests against a sandbox application; needs `DIDIT_SANDBOX_API_KEY`           |
| `pnpm lint`           | eslint and prettier                                                                     |
| `pnpm format`         | prettier, writing                                                                       |
| `pnpm typecheck`      | `tsc` strict on everything, and on the package without Node.js types                    |
| `pnpm build`          | ESM, CommonJS and declarations into `dist/` (tsup)                                      |
| `pnpm check:package`  | publint and are-the-types-wrong on the packed package                                   |
| `pnpm spec-sync`      | Download the upstream OpenAPI documents into `openapi/` (what the daily workflow runs)  |

## How the code is organised

- `openapi/`: the API contract. `verification.json`, `account.json` and `webhook-vectors.json` are upstream copies, never edited by hand. `overlay.json` holds the SDK naming (`x-didit-sdk`) for operations that do not carry it upstream yet. `deprecated-operations.json` keeps removed or renamed methods for at least one more minor version.
- `codegen/`: the generator (TypeScript, reads only `openapi/`) and the spec sync.
- `src/resources`, `src/types`, `tests/generated`, `api.md`: generated. Every file starts with `Code generated by codegen from openapi/*.json. DO NOT EDIT.`
- `src/core`: the hand-written client: configuration, HTTP, retries, errors, pagination, uploads, dates.
- `src/webhooks`: webhook verification and typed events. `src/authentication`: the Authentication helper.

## Changing the API surface

Never edit generated code. The API changes upstream (service-didit-verification and service-didit-auth update the OpenAPI documents in mintlify-docs), and the spec sync brings the change here:

1. `.github/workflows/spec-sync.yml` runs daily (and on demand). It downloads the documents, regenerates, runs every check and opens or updates the pull request `chore(spec): sync API spec YYYY-MM-DD` on the branch `chore/spec-sync`, with the added, removed and changed operations, the deprecations and the breaking changes. The title is always `chore(spec): ...` (DESIGN.md section 3.1); the commit and a `BEGIN_COMMIT_OVERRIDE` block in the description, which release-please reads after a squash merge, say `feat(spec)!` for a breaking sync, `feat(spec)` for one that adds or changes methods or types, and `chore(spec)` for documentation only. Keep that block when you edit the description.
2. A new operation without SDK naming fails the generator with a message that names it, and the pull request is opened as a draft. Add the naming to `openapi/overlay.json` (resource, method, auth, server and, for paths under `/v3/organization/{organization_id}/application/{application_id}/`, `scope: "application"`), push it to `chore/spec-sync`, and run `pnpm generate`. Ask for the same `x-didit-sdk` upstream, and add the entry to the six other SDK repositories.
3. A removed or renamed method stays as a deprecated method (`openapi/deprecated-operations.json`) with `remove_in` two minor versions after the version current at the sync, so at least one released minor version carries it as deprecated. The contract test fails once the package version reaches `remove_in`; then delete the entry, regenerate, and commit the removal as a breaking change. Until then, the hand-written tests and examples may keep calling the old name: eslint only warns about it, so the sync pull request stays green, and the type check fails once the name is removed. CI checks this on every pull request with a simulated sync that renames every server method and removes one (`codegen/tests/simulate-upstream.ts`).

While the sync pull request carries a commit that did not come from the workflow (a fix pushed by hand), the workflow leaves the branch alone, and a push to the branch during a run stops that run before it would overwrite the push.
For CI to run on the sync pull request, add the repository secret `SPEC_SYNC_TOKEN` (a fine-grained token with Contents and Pull requests read and write on this repository).

Changes to hand-written core behaviour that DESIGN.md describes (client options, errors, retries, pagination, webhooks, Authentication) are made in all seven SDK repositories, one pull request each, with DESIGN.md updated in the same words everywhere.

## Tests

Unit tests never touch the network: the HTTP layer is a `fetch` mock (`tests/helpers/mock-api.ts`), Authentication tests sign tokens with keys generated at run time, and webhook tests run the backend's own vectors.
The live smoke tests (`tests/live/`) run only with `DIDIT_SANDBOX_API_KEY` set (optional: `DIDIT_SANDBOX_WORKFLOW_ID`, `DIDIT_SANDBOX_BASE_URL`); in CI they run only when the CI workflow is started by hand.
Never commit secrets, API keys, tokens or real customer data; fixtures are synthetic, and synthetic webhook secrets start with `whsec_test_`.

## Commits and pull requests

Use [conventional commits](https://www.conventionalcommits.org): `fix:` (patch), `feat:` (minor), `feat!:` or a `BREAKING CHANGE:` footer (major; minor while 0.x), and `docs`, `test`, `refactor`, `perf`, `build`, `ci`, `chore` for the rest.
Public API changes need tests and a README update.
Every pull request says whether the same change is needed in the other six SDK repositories.

## Releases

Nothing is published before Alex's explicit approval and the 2026-11-01 Didit release. Until then the version stays 0.x.

1. Run the **Release** workflow (`.github/workflows/release-please.yml`) by hand. It opens the release pull request: the version bump in `package.json` and `src/core/version.ts`, and `CHANGELOG.md` generated from the commits (never edit it by hand).
2. Merge the release pull request, then run the **Release** workflow again. It creates the `vX.Y.Z` tag and the GitHub release, and its `publish` job waits for a reviewer of the GitHub environment `npm`.
3. Once approved, the job checks that the tag matches the package version, re-runs the generator check, the type check, the tests and the package checks on the tag, and publishes to npm with provenance.

One-time setup before the first release (a repository admin):

1. **Public repository.** npm publishes with provenance only from a public repository, so the publish job refuses to run while this one is private. On release day, after the full-history secret scan (the `Secret scan` CI job), make the repository public, then publish.
2. **npm.** Make sure the `@didit-protocol` organization exists on npmjs.com and that the publishers have 2FA. The package name `@didit-protocol/sdk-node` is free until the first publish.
3. **GitHub environment.** Create the environment `npm` (Settings, Environments) with required reviewers (Alex), and allow only the `main` branch and `v*` tags to deploy to it.
4. **First publish.** npm lets you configure a trusted publisher only for a package that exists. For the first release, add an environment secret `NPM_TOKEN` (a granular access token with publish rights on the `@didit-protocol` scope, short expiry) to the `npm` environment; the publish job uses it, still with provenance.
5. **Trusted publishing.** After the first publish, on npmjs.com open the package settings and add a trusted publisher: GitHub Actions, organization `didit-protocol`, repository `sdk-node`, workflow `release-please.yml`, environment `npm`. Then delete `NPM_TOKEN`, and set the package's publishing access to require 2FA and disallow tokens.
6. **Tokens for CI on bot pull requests (optional).** `RELEASE_PLEASE_TOKEN` and `SPEC_SYNC_TOKEN`: fine-grained tokens limited to this repository (Contents, Issues, Pull requests read and write), so that the release and spec sync pull requests get CI.
7. **Code owners.** Give the `@didit-protocol/backend` team write access (or change `.github/CODEOWNERS`).
8. **Security reports.** When the repository goes public, enable private vulnerability reporting (Settings, Code security), which `SECURITY.md` points to; GitHub offers it only on public repositories.
